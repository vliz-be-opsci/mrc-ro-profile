VLIZ MRC RO-Crate Profile — Specification

  • Profile URI: https://w3id.org/vliz-be-opsci/crate-profiles/mrc-ro-profile/0.1
  • Profile of: MRC Ro-Crate
  • Version: 0.1
  • Status: Draft
  • Author: Flanders Marine Institute (VLIZ), Marine Robotics Center

1. Introduction

This profile defines how to package and publish datasets generated by the activities of the VLIZ Marine Robotics Center (MRC) as RO-Crates.

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY” and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

This document distinguishes two things that are easy to confuse:

  1. The profile’s own resources (section 2): the files shipped in the Profile Crate that define the profile. They exist once, for everyone.
  2. The content of a conforming crate (section 3): what every crate that claims conformance to this profile MUST, SHOULD or MAY contain. These requirements are only expressed in this document and in the profile’s SHACL shapes. They are not expressed as resources of the Profile Crate.

2. Resources of the profile

The Profile Crate gathers the following resources. Each is declared with a ResourceDescriptor using the roles of the Profiles Vocabulary.

Resource Role Purpose
SPEC.md (this document) specification Normative human-readable description of the profile.
mrco.shacl.ttl constraints SHACL shapes. Every conforming crate MUST validate against them (see 3.3).
mrco.profile.vocab.ttl vocabulary Vocabulary introduced by the profile itself, including the class ClosureGraph (see 3.4).

3. Requirements on conforming crates

A crate is a conforming crate if it satisfies all MUST-level requirements in this section.

3.1 Base specification

A conforming crate MUST be a valid RO-Crate and MUST declare conformance to MRC RO-Profile on the RO-Crate Metadata Descriptor (ro-crate-metadata.json).

3.2 Declaring conformance

The Root Data Entity of a conforming crate:

  • MUST declare conformsTo with the profile URI given at the top of this document.
  • MAY declare conformance to further profiles. conformsTo is then an array.

The crate MUST contain a contextual entity for the profile, with @type including Profile:

{
  "@id": "./",
  "@type": "Dataset",
  "conformsTo": { "@id": "https://w3id.org/vliz-be-opsci/crate-profiles/mrc-ro-profile/0.1" }
},
{
  "@id": "https://w3id.org/vliz-be-opsci/crate-profiles/mrc-ro-profile/0.1",
  "@type": ["CreativeWork", "Profile"],
  "name": "VLIZ MRC RO Crate Profile",
  "version": "0.1.0"
}

A conforming crate MAY include a snapshot copy of this Profile Crate and indicate it using distribution on the profile entity. This is RECOMMENDED for archival purposes.

3.3 Constraints

The metadata of a conforming crate MUST validate against the SHACL shapes in mrco.shacl.ttl. These shapes are the normative statement of which types and properties are required, recommended or allowed in the crate’s metadata. Where this document and the shapes disagree, the shapes take precedence for the properties they cover. Metadata MAY not be limited to the contents of the ro-crate-metadata.json a the root of the crate.

3.4 Closure graph (optional)

A closure graph is an RDF file that describes the resources of the namespace https://infra.mrc.vliz.be/ that are used in the crate, such as the sensors and platforms used to make the observations in the dataset, so that the crate can be understood without resolving those identifiers online.

Presence.

  • A conforming crate MAY contain a closure graph.
  • A conforming crate MUST NOT contain more than one closure graph.
  • A crate without a closure graph is still a conforming crate. Consumers then resolve the identifiers of the namespace online.

Identification. If present, the closure graph:

  • MUST be a data entity of type File that is referenced from the Root Data Entity using hasPart.
  • MUST declare additionalType with the value mrcp:ClosureGraph (full URI: see the profile vocabulary).
  • MUST declare encodingFormat for an RDF serialization, for example text/turtle.
{
  "@id": "./",
  "hasPart": [ { "@id": "closure.ttl" } ]
},
{
  "@id": "closure.ttl",
  "@type": "File",
  "name": "Closure graph",
  "additionalType": { "@id": "https://infra.mrc.vliz.be/profile/vocab#ClosureGraph" },
  "encodingFormat": "text/turtle"
}

Content. If present, the closure graph:

  • SHOULD describe every resource of the namespace https://infra.mrc.vliz.be/ that is referenced by the crate.
  • SHOULD validate against the shapes in mrco.shacl.ttl.

Consumers. A consumer that finds a closure graph SHOULD prefer it over online resolution of the identifiers it covers. It MAY fall back to online resolution for identifiers not covered.

3.5 Observation Collection

Each http://schema.org/Dataset and http://schema.org/File in a conforming crate MAY be additionally typed as a http://www.w3.org/ns/sosa/ObservationCollection. Each such http://schema.org/Dataset or http://schema.org/File MUST then also list at least one http://www.w3.org/ns/sosa/Sensor using the http://www.w3.org/ns/sosa/madeBySensor property on the ObservationCollection.

5. Versioning

The profile URI is versioned as MAJOR.MINOR. Patch versions of the Profile Crate (the version property) do not change the profile URI. Updates MAY add terms and SHOULD NOT remove or redefine terms already published.
